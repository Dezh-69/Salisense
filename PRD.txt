1. Purpose of This Document
This document defines the product requirements for the Flutter mobile application component of the Automated Salinity Monitoring and Controlled Balancing System. It serves two purposes. First, it is a documentation deliverable that describes the mobile application's requirements in one place for the capstone paper. Second, it is a build reference the development team can use while implementing the Flutter application, so the app matches what the manuscript already commits to.
2. Background
Small to medium scale fishpond operators in the Philippines commonly rely on manual salinity monitoring and periodic water exchange. This approach is reactive, labor intensive, and prone to delayed intervention during rapid salinity changes. The system replaces this manual practice with continuous sensing and automatic correction, and gives farmers a mobile application to observe salinity conditions and system activity without needing to be physically present at the tank.
3. Product Objective
The manuscript states the mobile application objective as: "a mobile application interface accessible over the internet through a Firebase Realtime Database for real-time monitoring and data log viewing." This is Objective 2.4 of the study.
4. Target User
The Fish Farmer is the primary and only operational actor of the mobile application. The use case diagram in the manuscript defines three actor interactions: View Real-Time Salinity, View System Status, and View Salinity Logs. All three are performed by reading data from the Firebase Realtime Database through the mobile application.
IT Experts and IT Faculty appear in the manuscript as respondents during the Phase 5 evaluation, assessing technical architecture, code quality, and adherence to academic and engineering standards. They are evaluators of the system, not operational users of the app in normal use.

6. System Architecture and Data Flow
The ESP32 and the Flutter application connect to the same Firebase Realtime Database independently. The ESP32 writes sensor readings and pump status over the internet using the FirebaseClient library's UserAuth provider, authenticated with a dedicated device account. The Flutter application reads from the same database using FlutterFire, authenticated with its own separate app account. The app does not connect to the ESP32 directly.
Firebase security rules enforce the separation: write access on the sensor data path is restricted to the device account, and read access is restricted to the app account. Neither account can perform the other's role.
The ESP32 and the app each require their own internet connection. They do not need to share a network. If the ESP32 loses its internet connection, it continues automated correction using the thresholds already loaded, and only remote monitoring through the app is affected until connectivity returns (FT-10). If the app loses its connection, only its ability to read monitoring data is affected. The ESP32's correction cycle is not affected.
The backend runs on the free Spark tier of Firebase Realtime Database.

9. Alerts and Fault Handling
Fault is defined in the manuscript as a condition where the EC sensor returns a disconnected or out of range reading, or an activated pump fails to produce a measurable salinity change within its timeout. A fault condition causes the ESP32 to deactivate all pumps and transmit an alert to the app. Overcorrection is defined separately, as a condition where a completed correction cycle pushes salinity past the activation threshold on the opposite side.
AlertTrigger ConditionApp BehaviorSensor faultEC sensor returns a disconnected or out of range reading.Sensor fault alert displayed, within 10 seconds per FT-06.Pump faultActivated pump does not change salinity by at least 0.5 ppt within a 24-second timeout.Pump fault alert displayed.Low reservoirFloat sensor signals low fill on either reservoir during operation.Low reservoir alert displayed before the affected pump runs dry.OvercorrectionAfter a completed correction cycle, salinity crosses the activation threshold on the opposite side.Overcorrection alert displayed.

11. Constraints and Assumptions
11.1 Constraints
The app is limited to reading monitoring data. It cannot send commands or change settings on the ESP32. It requires its own internet connection, separate from the ESP32's network.
11.2 Assumptions
The mobile device used for the Flutter application is assumed to be researcher owned. It is excluded from the prototype hardware cost estimate in the manuscript's cost analysis.
12. Gaps Not Specified in the Manuscript
The manuscript defines what the app must show and the data path it reads from, but it does not specify how the app should be built at the screen level. The items below are not requirements. They are gaps a development team would need to resolve before or during implementation, and they are flagged here rather than filled in with invented specifications.
ItemNoteScreen layout and navigationThe manuscript lists what data the app shows but does not specify the number of screens, their layout, or how the farmer navigates between them.App refresh intervalThe ESP32 side is fully specified: a 5-second control cycle and 30-second SPIFFS logging interval. The manuscript does not state whether the app uses a live Firebase listener or polls at a fixed interval.Alert delivery mechanismThe manuscript states alerts are "displayed on the mobile application" but does not specify push notification, in-app banner, sound, or vibration.Farmer accountsThe app authenticates using a single app-level account through FlutterFire. The manuscript does not describe individual farmer logins or multi-user access.Behavior during lost connectionThe manuscript states that a lost app connection affects monitoring but does not specify what the app shows during that period, for example a cached last reading, an error state, or a blank screen.DistributionThe manuscript does not specify whether the app will be distributed through an app store, a direct install file, or side-loaded only for evaluation respondents.Log query range or exportThe manuscript states the log is viewable "at any time during or after a session" but does not specify date filtering, search, or export.Overcorrection alert traceabilityThe overcorrection alert is defined in Chapter I and referenced in the Description of the Prototype, but it is not mapped to any numbered case in Table 3 of the manuscript. FT-06, FT-08, and FT-09 cover the other three app alerts. This is a test coverage gap worth raising with the adviser before Phase 4 testing.FR-10 verificationNo control input path back to the ESP32 (FR-10) is stated as a design property but is not tied to any blackbox test case in Table 3. Absence of a control feature is not naturally a pass or fail input or output test. It is better suited to a code or architecture review, which the manuscript already schedules under the IT Expert evaluation in Phase 5.
